# JSON records and accounting

The branch is rebased onto perf-batch `f363ac01`, including VM round 4, text indexing and startup-parser changes. Small JSON skips record setup below 2 KiB and reservations below 8 KiB, uses direct accounting for flat documents, and adds no tracked heap storage for field tables. The VM and bytecode changes belong to upstream.

Only this summary is tracked in Git. All supporting results, profiles, binaries and exports live under `/Volumes/AI/Work/xipkit/vibescript.rs/.cache/mgomes/json-records/`. The complete prior evidence is in `pre-perf-batch/results/`; the fresh rebase audit and layout experiment are in `perf-batch/`. ## Records

For documents of at least 2 KiB, `JSON.parse_as` follows statically known array, tuple, hash and shape containers while parsing. Names are imported at their original source materialization point and reused across array elements through lazy `Fields` tables. The root record needs no sharing table because it is built once. A small cache of schema paths avoids repeated shape searches while visiting nested records. Required closed shapes reserve their exact pair count at the first insertion. Optional/open shapes retain ordinary growth because the number of supplied fields is not known. Smaller documents skip the schema cursor, field tables and capacity setup, retaining the ordinary parser's type validation and hash growth. The result remains an ordinary hash, populated in source order, including the existing duplicate-key replacement behavior.

`Fields::of`, `key` and `len` remain compatible. The additive lazy-slot interface uses inline storage for up to eight names and supports tracked storage for larger callers. JSON now uses only the inline form: sixteen chunks of eight slots bound schema sharing at 128 names without allocating field-table metadata. Further names use the ordinary key cache. The follow-up adds `Fields::forget`, which releases one lazy name and updates completion bookkeeping. Existing import and lookup methods remain compatible. Tests cover source order, duplicate and escaped names, long names, shared names across shapes, open-shape extras, exact capacity, overflow, 8/9/16/17/65-field shapes and complete release. New tests check both sides of the record cutoff and every slot of a 257-field schema, including zero tracked allocation for the tables.

Schema storage belongs to a separate record-parsing stack frame, so small and untyped calls do not initialize it. Key and scalar caches initialize independently. Non-indexed strings compile without cache setup, and failure formatting is kept out of the successful parse path. Short-key hashing processes four bytes at a time; a test checks its exact equivalence to the original cache sets, preserving collisions and eviction behavior.

Escaped strings decode outside the scanner fast path. Single decoded bytes use spare buffer capacity directly, preserving growth and charge points. The writer initializes short escapes in a checked two-byte spare slice and publishes its length once, avoiding both repeated vector growth checks and the hot temporary-array reload seen in the x86 profile. The quota oracle checks the same partial output and accounting at every boundary.

Streamed validation keeps one inline proof for a closed record with at most fifteen scalar fields. After a full check, subsequent records must have the same keys in the same source order and every scalar value must still match its type. They then reuse the exact normalization charge computed by that full check. Different layouts and unsupported or mismatching types use the ordinary checker. The cache owns only type references and field indexes, so it cannot retain parsed values or add tracked heap bytes. The exhaustive normalization oracle covers reordered keys, nullable and mixed scalar values, missing and extra fields, invalid types, escaped names, and duplicate arrays. A paired M4 profile of the preceding runtime attributed 9.09% of transform CPU samples to type validation. Eight-round focused runs of this change reduce portable unlimited transform from 34.84 to 32.97 µs on M4 and 49.17 to 46.83 µs on Shannon.

The indexed parser also shares repeated unescaped scalar strings of at most 64 bytes in a bounded two-way cache. Numbered strings bypass this cache so unique identifiers do not churn it. The cache copies strings into ordinary owned values; it never retains slices of the input. Duplicate object replacement clears scalar entries before the next allocation so discarded subtrees do not remain live. A bounded reference-count scan also removes field names owned only by parser caches, while names owned by surviving output records continue to share. Parse errors clear scalar entries and field tables before diagnostic allocation. Regression tests cover long names in replaced indexed and flat subtrees, surviving sharing after duplicate keys, and quota boundaries around a long error diagnostic. A nine-field duplicate-subtree probe previously raised peak tracked memory from the baseline’s 24,198 bytes to 25,454; it now peaks at 23,906 bytes. The regression input and before/after observations are included in the evidence.

## Accounting order

Step allowances end before the next existing 16-step checkpoint and never exceed remaining quota. Local draws settle before every mutable context operation and on drop. A charge that crosses either boundary uses the original `CallContext::charge`, including its multi-step overshoot and latched error. Existing string decoding/encoding batches continue to use their settled context, avoiding an extra wrapper on each escape. No public charging API changes.

Indexed payloads of at least 8 KiB use unescaped token copies that reserve only available memory headroom for the backing bytes and value header together. Credit acquisition cannot fail and does not publish a speculative peak. Each draw performs the original checkpoint; an insufficient draw releases unused credit and calls the original reservation at exactly that point, after the same steps. Actual live peaks are accumulated locally and published before return, error or another allocator. The two pieces share one retained charge, removing an atomic release and ledger reference count per string. Reservation scopes cannot call host code or expose speculative credit. Small and flat documents compile against `CallContext` directly, eliminating both reservation setup and a per-operation bypass branch. Key and scalar cache lookups are separately compiled, and decoded-key adoption stays outside the escape loop.

The parser oracle compares separately compiled direct and reserved accounting paths; the writer oracle disables its reservations. It compares every step quota crossed with every byte quota for small valid and invalid documents, typed/untyped and indexed/portable paths. Comparisons include the value or error, parser position, syntax failure, partial writer output, steps, peak/retained memory and subsequent latched error. Separate tests cover empty strings, a token larger than the 4 KiB chunk, and cancellation/deadline boundaries. Intentional storage reductions from records/string sharing are independently audited against the baseline.

Additional probes check [singleton shapes](/Volumes/AI/Work/xipkit/vibescript.rs/.cache/mgomes/json-records/pre-perf-batch/results/width-counters.json) and [arrays of wide shapes](/Volumes/AI/Work/xipkit/vibescript.rs/.cache/mgomes/json-records/pre-perf-batch/results/array-width-counters.json), including 129 and 257 fields beyond the inline sharing bound. The former 256–2,048-byte field-table allocations have been removed; the bounded tables occupy parser stack storage. The before/after probes compare output, steps, peak and retained bytes against `a23d4ece`. These probes use records that satisfy their declared shape. Exact preallocation still reserves the declared capacity before normalization: additional rescued-error probes of invalid closed shapes show temporary increases of 32–208 bytes when fields are missing or extra. That cost belongs to the record buffer, not the bounded field tables; the accounting oracle compares batching with the same storage strategy.

## Previous acceptance measurements

Before the perf-batch rebase, paired measurements compare runtime `42a467ea` with upstream `a23d4ece` on Darwin (Apple M4) and Shannon (Intel Core Ultra 9 285H). Each host ran `scripts/compare.py --rounds 8 --target-ms 250` with the JSON and core suites, rotating portable/SIMD and before/after binaries. The updated upstream launcher uses an identical executable path for every paired variant. Shannon pairs are pinned to performance core 2 (5.4 GHz maximum) to avoid migration between performance and efficiency cores; the environment manifest records affinity. The earlier full run passed every JSON case but measured a +3.34% M4 portable string-build control and a +3.83% Shannon SIMD uppercase control; it is retained separately, and this full rerun uses the stabilized launcher. No gate ran concurrently; interrupted earlier attempts are excluded. No measurements ran on Vinci.

All **640** comparisons pass the +3% time limit: the largest change is +2.88% on M4 and +1.91% on Shannon. Every 1 KiB JSON case passes the +3% limit: M4 ranges from -6.27% to +0.17%, and Shannon from -9.85% to -5.43%. The three originally reported M4 regressions now measure -0.97% (portable shape/metered), -3.51% (SIMD shape/metered), and -0.16% (portable array/unlimited).
