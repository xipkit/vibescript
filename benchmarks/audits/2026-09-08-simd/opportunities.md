# SIMD opportunities in Vibescript

Assessed commit: [`e6f1fca90c012885453a6c413c0826f6abff1f32`](https://github.com/xipkit/vibescript/tree/e6f1fca90c012885453a6c413c0826f6abff1f32).

The strongest candidates are custom byte scans in string and JSON helpers. These rankings are code-based predictions, not measured speedups. They do not establish support or performance for a particular Go 1.27 SIMD API. Measurements from the separate test-only ARM64 ASCII-classifier probe should be reported separately.

## Accounting implications

An allocation-free byte-classification helper can remain below the existing accounting boundary: callers keep their logical input/output charges and reservations, while the helper reads the same bytes faster. Do not discount steps by vector width. Faster execution should not make sandbox quotas CPU-dependent.

For transforms, keep preflight reservations before allocation and account for simultaneously live input, output and scratch. Avoid an input-sized packed copy just to feed a vector API. A fixed-width local vector or small bounded tail buffer is a different resource profile from an input-sized heap slice; verify escape behavior and allocation counts for the chosen implementation.

An implementation should compare scalar and SIMD paths for results, quota thresholds and errors, including boundary lengths, invalid UTF-8, cancellation, escaping and output retention. Low-level loads must remain in bounds on the final partial vector.

## Lower-priority areas

Numeric arrays are not packed numeric buffers. [`Value`](https://github.com/xipkit/vibescript/blob/e6f1fca90c012885453a6c413c0826f6abff1f32/vibes/value/value.go#L70) contains a tag, an `any` payload and scalar bits; arrays store `[]Value`. Gathering or packing numbers introduces work, and packing requires additional accounted memory.

[`arraySum`](https://github.com/xipkit/vibescript/blob/e6f1fca90c012885453a6c413c0826f6abff1f32/internal/runtime/members_array.go#L2545) supports arbitrary blocks, mixed operands, per-element steps, big-integer guards and peak accumulator checks. [Integer overflow promotes to arbitrary precision, while mixed numeric addition uses floats](https://github.com/xipkit/vibescript/blob/e6f1fca90c012885453a6c413c0826f6abff1f32/internal/runtime/values.go#L737). Reordering a float reduction can change its result; regrouping integer additions can change temporary promotion and resource charges. Extrema also [preserve the first element on ties](https://github.com/xipkit/vibescript/blob/e6f1fca90c012885453a6c413c0826f6abff1f32/internal/runtime/members_array.go#L633). Searches have tested [per-element charging and early exits](https://github.com/xipkit/vibescript/blob/e6f1fca90c012885453a6c413c0826f6abff1f32/internal/runtime/array_scan_metering_test.go#L47). These need a separate semantic specialization design before SIMD is likely worthwhile.

Checker analysis, environment lookup and memory-graph estimation primarily traverse maps, pointers and tagged values. Avoiding repeated work and improving layout remain more direct approaches than vector arithmetic there.

## Standard-library overlap

Vibescript already delegates [ASCII substring search to `strings.Index`](https://github.com/xipkit/vibescript/blob/e6f1fca90c012885453a6c413c0826f6abff1f32/internal/runtime/members_string.go#L1250), [line search to `strings.IndexByte`](https://github.com/xipkit/vibescript/blob/e6f1fca90c012885453a6c413c0826f6abff1f32/internal/runtime/members_string.go#L343), and [replacement counting to `strings.Count`](https://github.com/xipkit/vibescript/blob/e6f1fca90c012885453a6c413c0826f6abff1f32/internal/runtime/members_string.go#L2206). On the inspected local Go 1.26.3 ARM64 installation, the underlying `internal/bytealg` index-byte and byte-count routines already use vector assembly. New custom SIMD should therefore target the scalar classification surrounding those calls, rather than assume these standard-library operations are currently scalar.
